# Item Types

Research notes on DevStash's 7 built-in item types — what's in the schema, what's seeded, and what's actually implemented today. Generated by `/research item-types-research`.

Sources: [project-overview.md](../context/project-overview.md), [schema.prisma](../prisma/schema.prisma), [item-types.ts](../src/features/items/lib/item-types.ts), [seed.ts](../prisma/seed.ts).

## Naming: spec vs. database

`project-overview.md` names the 7 types in the singular (Snippet, Prompt, Note, Command, File, Image, URL). The actual seeded `ItemType` rows (`prisma/seed.ts`) use different names — plural, and "Links" instead of "URL":

| Spec name (project-overview.md) | DB name (seeded) |
| -------------------------------- | ----------------- |
| Snippet                          | Snippets          |
| Prompt                           | Prompts           |
| Note                             | Notes             |
| Command                          | Commands          |
| File                             | Files             |
| Image                            | Images            |
| URL                              | Links             |

The tables below use the DB names, since those are what the running app and sidebar actually show.

## Per-type reference

| Name | Icon (lucide) | Color | Pro-gated | Purpose | Key fields |
| ---- | -------------- | ----- | --------- | ------- | ---------- |
| Snippets | `Code` | `#3b82f6` | No | Reusable code snippets | `content`, `language` |
| Prompts | `Sparkles` | `#8b5cf6` | No | AI prompts / workflow instructions | `content` |
| Commands | `Terminal` | `#f97316` | No | Shell / CLI commands | `content`, `language` |
| Notes | `StickyNote` | `#fde047` | No | Free-form text notes | `content` |
| Files | `File` | `#6b7280` | **Yes** | Uploaded documents/templates | `fileUrl`, `fileName`, `fileSize` |
| Images | `Image` | `#ec4899` | **Yes** | Uploaded images | `fileUrl`, `fileName`, `fileSize` |
| Links | `Link` | `#10b981` | No | Saved URLs / bookmarks | `url` |

Icon/color source of truth is `ItemType.icon` / `ItemType.color` (both nullable `String?` on the model) — `SYSTEM_ITEM_TYPES` in `prisma/seed.ts` is what actually populates them for the 7 built-ins. `ITEM_TYPE_ICONS` in `item-types.ts` is just the lucide name→component lookup used at render time; if an icon name isn't in that map (or is null), `ItemTypeIcon` falls back to the generic `File` icon, and a null color falls back to `currentColor` (icon) or `var(--border)` (row accent).

**Pro gating** has no column on `item_types` — `PRO_ITEM_TYPE_NAMES` in `item-types.ts` hardcodes `Files` and `Images` by name as the one place to change when a real plan model lands. Per the commit history (`current-feature.md`), this is a *known* deviation from `project-overview.md`'s pricing table, which puts image uploads on Free and only file uploads on Pro — the sidebar badge follows the hardcoded set, not the pricing table.

## Classification: text vs. file vs. URL

`Item.contentType` is a plain `String` (`"text" | "file"`, per the schema comment), not an enum, and is independent of `typeId` — nothing in the schema forces a given `ItemType` to use a particular `contentType`. In practice:

- **text** — `content` holds the payload. Used today by Snippets, Prompts, Commands, Notes (Commands/Snippets additionally set `language` for syntax highlighting, once implemented).
- **file** — `fileUrl` / `fileName` / `fileSize` hold the upload. Intended for Files and Images; **no seed item currently uses this path** — the schema and Pro gate exist, but nothing exercises `contentType: "file"` yet.
- **URL** — `url` holds the link. Used by Links. Not a distinct `contentType` value in the schema; a Links item is seeded with `contentType: "text"` and `content: null`, `url` set.

`prisma/seed.ts` sets `contentType: "text"` unconditionally for every seed item (see `main()`), regardless of type — so even Links items are nominally `"text"` with the URL carried in the separate `url` field. Notes, Files and Images have **zero** seeded example items (`COLLECTIONS` only uses Snippets, Prompts, Commands and Links) — those three types exist in the type table but have no real data to look at.

## Shared properties

Every item, regardless of type, carries: `id`, `title`, `description`, `isFavorite`, `isPinned`, `userId`, `typeId` (→ `ItemType`, `onDelete: Restrict`), `collectionId` (→ `Collection`, `onDelete: SetNull`), `tags` (through `ItemTag`), `createdAt`/`updatedAt`. `language` exists on every item regardless of type (nullable), not just code-shaped ones.

## Display differences (as implemented today)

There's currently **one** rendering path for all 7 types — `ItemRow` — and it does not branch on `contentType`, `url`, or `fileUrl` at all:

- `ItemTypeIcon` renders the type's icon + color (or the `File`/`currentColor` fallback) in a fixed 36px badge.
- The row shows `title`, `description` (1 line, clamped), `tags`, pinned/favorite markers, and a relative-ish short date. That's it — no content preview, no syntax highlighting, no thumbnail for Images, no favicon/domain for Links.
- The list query (`ITEM_SUMMARY_SELECT` in `items.ts`) deliberately excludes `content`, `url`, `fileUrl`, `fileName`, `fileSize`, `language` — the comment notes item **detail** views will need their own, fuller fetch. That detail view doesn't exist yet: routes like `/items/[type]/[id]` are still 404 by design (per `CLAUDE.md`'s "Deliberate current state").

So today, type-specific display is limited to icon + accent color. Any type-aware rendering (code highlighting for Snippets/Commands, image thumbnails, link previews, file download affordances) is unbuilt.
